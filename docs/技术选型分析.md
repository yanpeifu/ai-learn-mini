## 0. 结论速览

**推荐组合**：

| 层 | 选型 |
| --- | --- |
| 小程序前端 | Taro 4 + React 18 + TypeScript |
| 后端 | Python 3.11+ / FastAPI |
| 数据库 | 开发期 SQLite，生产 PostgreSQL |
| 向量检索 | 开发期 Chroma，生产 pgvector（复用 PostgreSQL） |
| 大模型 | DeepSeek（开发期）+ 适配层，产品化优先切阿里云百炼/火山引擎 |
| 部署 | 轻量云服务器 + Docker Compose |
| 包管理 / 规范 | pnpm + ESLint + Prettier + TypeScript strict |

**一句话理由**：这套组合在"一个人、两三周跑通闭环"的约束下，把学习成本和运维负担压到最低，同时保留了产品化时换模型、换数据库、多端发布的余地。

**最重要的三个判断**（详见后文）：

1. **前端选 Taro 而不是原生，主要是为了"不被锁死在微信端"和类型安全**，代价是构建链路更复杂。如果你确定只做微信且不熟 React，原生反而是更好的选择——第 2.4 节给了判断标准。
2. **后端选 Python 而不是 Node，核心原因不是语言偏好，而是 AI 生态**。LLM SDK、向量库、文档解析、评测工具全部是 Python 优先，一个人做 AI 应用时这个优势会被放大。
3. **模型供应商的选择不只是价格问题**。产品化阶段申请微信"深度合成"类目需要技术方提供《互联网信息服务算法备案》和《合作协议》，阿里云、火山引擎这类大厂有成熟的对接流程，而纯 API 供应商不一定提供。**选型时要为这一步留后路。**

## 1. 选型的约束条件

所有推荐都基于以下约束，如果约束变了，结论也可能变：

| 约束 | 内容 | 对选型的影响 |
| --- | --- | --- |
| 人力 | 一个人开发 | 优先选"学习成本低、坑少、文档全"的方案，而不是"性能最强"的 |
| 阶段 | 作品集优先，后续产品化 | 方案要能平滑演进，不能只适合做 demo |
| 平台 | 微信小程序优先 | 但不排除未来出 H5 |
| MVP 范围 | 只做文字输入 | 不需要视频/音频解析的重型依赖 |
| 成本 | 个人承担 | 优先选免费额度和低固定成本方案 |
| 时间 | 2–3 周出 V0.1 | 成熟生态 > 自研轮子 |

## 2. 小程序前端框架选型

### 2.1 候选方案

| 方案 | 出身 | 技术心智 | 当前状态 |
| --- | --- | --- | --- |
| 原生小程序 | 微信官方 | WXML / WXSS / JS / TS | 官方持续维护，Skyline 渲染引擎持续演进 |
| Taro 4 | 京东 | React / Vue | 活跃维护 |
| uni-app | DCloud | Vue | 活跃维护 |
| Wepy | 腾讯 | Vue 1.x 风格 | 已停止维护 |
| Remax | 阿里 | React | 基本不活跃 |
| Chameleon | 滴滴 | 多语法 | 基本不活跃 |

**先排除三个**：Wepy 已停止维护；Remax 和 Chameleon 社区基本停滞。选框架的第一原则是"两年后还有人维护"，这三个直接出局，不用再比较技术细节。

### 2.2 核心对比

| 对比维度 | 原生小程序 | Taro 4 | uni-app |
| --- | --- | --- | --- |
| 语言 / 心智 | 微信自有语法 | React 或 Vue | Vue |
| 只做微信时的上手成本 | 最低 | 中 | 中 |
| 多端能力 | 弱（需重构） | 微信/支付宝/抖音/H5/RN | 最全（含 App、鸿蒙） |
| 运行性能 | 最佳（可用 Skyline） | 好（编译期优化，接近原生） | 好 |
| 组件生态 | 官方组件 + 少量三方 | 可复用 React/npm 生态（NutUI 等） | DCloud 插件市场丰富 |
| TypeScript 支持 | 支持，但类型覆盖一般 | 一等公民 | 支持较好 |
| 调试体验 | 最直接，无中间层 | 多一层编译，偶有映射问题 | 多一层编译 |
| 构建链路复杂度 | 无（微信开发者工具即可） | 中（Vite + 编译插件） | 中（HBuilderX / CLI） |
| 与 AI 辅助编码配合 | 一般（语料相对少） | 好（React 语料极多） | 好（Vue 语料极多） |
| 招人 / 作品集观感 | 中 | 较高（体现跨端工程能力） | 较高 |
| 主要风险 | 平台锁定 | 框架版本升级的兼容坑 | 部分高级能力需付费/云服务 |

### 2.3 分析

**原生小程序**的优势被低估了。它没有构建链路，微信开发者工具打开就能写，遇到问题直接查官方文档，性能上限最高。对一个人做单一平台的产品来说，这是"最少意外"的路径。它的真实代价是：一旦要出 H5 或 App，代码基本要重写。

**Taro 4** 的价值在于三点：用 React 写，能吃到整个 npm 生态（图表、Markdown 渲染、工具库直接可用）；一份代码可编译到 H5，为将来做准备；TypeScript 支持完善，这在"大模型返回结构化 JSON"的场景里能显著减少运行时错误。代价是构建链路更复杂，偶尔会遇到编译产物和预期不一致的问题，排查需要经验。

**uni-app** 的多端能力最强（连 App 和鸿蒙都覆盖），如果你未来明确要做 App，它是唯一顺滑的选择。但它的部分高级能力依赖 DCloud 的云服务和 HBuilderX 生态，对纯代码工作流不如 Taro 顺手。

### 2.4 推荐：Taro 4 + React + TypeScript

**理由**：

1. **与"微信优先但可能多端"的规划匹配**。未来出 H5 版本（比如做小红书引流落地页）几乎是零成本。
2. **降低技术风险的方式是复用生态**。答题页的图表、Markdown 渲染、动画库，React 生态都有成熟实现，不用自己写。
3. **有同构开源项目可参考**。[liyupi/yu-ai-learn](https://github.com/liyupi/yu-ai-learn) 用的正是 Taro + React + FastAPI + DeepSeek，遇到问题时这条参照路径很值钱。
4. **TypeScript 在这个项目里有实际收益**。题目、选项、答题记录的字段很多，且都来自大模型输出，类型校验能在开发期就拦住大量低级错误。
5. **作品集角度更有说服力**。跨端框架 + 类型系统比原生更能体现工程能力。

**但这个推荐有前提。如果你满足以下任意一条，请改用原生小程序**：

- 你完全不熟悉 React（学 Taro 等于同时学 React + 框架，双倍成本）
- 你确定这辈子只做微信端，不打算出 H5
- 你更看重"两周内绝对能跑通"，不想承担构建链路的任何风险

**如果你熟悉 Vue 而不是 React**：直接用 uni-app，不要为了推荐而硬切 React。用熟悉的心智模型在两周内交付，比用"更推荐的框架"卡住强得多。

## 3. 后端技术选型

### 3.1 候选方案对比

| 方案 | 优势 | 劣势 | 适合本项目的程度 |
| --- | --- | --- | --- |
| **Python + FastAPI** | AI/LLM 生态最强；原生异步；自动生成 OpenAPI 文档；Pydantic 与"大模型输出校验"天然契合 | 单纯的高并发性能不如 Go；运行环境需管理 | ★★★★★ |
| Python + Django | 全功能（ORM、Admin 后台、鉴权）；生态成熟 | 偏重；异步支持较新；对纯 API 服务略笨重 | ★★★★☆（若需要后台管理） |
| Node.js + NestJS | 与前端统一 TypeScript；工程结构规范；生态好 | AI 生态弱于 Python；学习成本高 | ★★★☆☆ |
| Node.js + Express/Koa | 轻量灵活、上手快 | 缺少约定，项目稍大就失控 | ★★☆☆☆ |
| Go + Gin | 性能极佳、单二进制部署、资源占用低 | AI 生态弱；开发速度慢；一人开发效率低 | ★★☆☆☆ |
| Java + Spring Boot | 企业级生态、稳定 | 重、启动慢、一人开发效率最低 | ★☆☆☆☆ |
| 微信云函数 / 云开发 | 免运维、与微信集成好 | 以 Node.js 为主；本地调试体验一般；成本随调用量增长；被平台绑定 | ★★★☆☆（原型可用） |

### 3.2 推荐：Python 3.11+ / FastAPI

**核心理由不是语言偏好，而是 AI 应用的技术生态分布**：

1. **所有 LLM 与向量库的 Python SDK 都是第一等公民**。DeepSeek、通义、豆包都提供 OpenAI 兼容接口，Python 客户端最稳定。
2. **Pydantic 解决了这个项目最核心的技术问题**。大模型返回的是"不太可靠的 JSON"，Pydantic 的模型校验能在解析阶段就把结构错误拦住，并且可以配合重试提示词做自动修复。这是选 FastAPI 最具体、最实际的理由。
3. **异步 I/O 正好匹配本项目的负载特征**。这个应用的瓶颈是"等待大模型返回"，不是 CPU 计算，async/await 能让服务器在等待期间处理其他请求。
4. **自动生成 API 文档**。FastAPI 自带 Swagger UI，前后端联调时不用手写接口文档，对这一个人既是前端又是后端的情况帮助很大。
5. **你已有 Python 项目经验**（LangGroupRag 等），复用已有认知能直接缩短工期。

**什么时候该选别的**：

- 如果你更希望"前端后端都用 TypeScript，类型定义共享"→ 选 NestJS，接受 AI 生态的损失
- 如果你需要现成的可视化管理后台（比如查看用户、手动修题）→ 用 Django，直接白送一个 Admin 界面。**这一条值得认真考虑**：产品的后期一定会需要"人工复核被举报的题目"这个功能，Django Admin 能省掉一整周的后台开发
- 如果你完全不想碰服务器 → 微信云函数起步，但要接受后续迁移成本

## 4. 数据库与向量检索选型

这块单独拎出来讲，因为它有一个容易踩的坑：**很多人会同时引入关系数据库 + 独立向量数据库，对一个人来说这是不必要的运维负担。**

### 4.1 关系型数据库

| 方案 | 优势 | 劣势 | 推荐场景 |
| --- | --- | --- | --- |
| **PostgreSQL** | 功能最强；JSONB 适合存题目结构；原生支持向量扩展 pgvector；SQL 表达力强，适合做复盘报告的聚合统计 | 相比 MySQL 国内云厂商运维资料稍少 | ✅ 生产环境推荐 |
| MySQL | 生态成熟；国内云厂商支持最好；资料最多 | 向量能力弱（需另搭向量库）；JSON 处理不如 PG 顺手 | 云厂商绑定时的备选 |
| SQLite | 零运维、单文件、开发极快 | 并发写入能力弱；不适合生产 | ✅ 开发期推荐 |
| MongoDB | 文档模型灵活，早期不用设计表结构 | 复盘报告需要多表聚合统计，文档模型很别扭 | 不推荐 |

**推荐策略**：**开发期用 SQLite，生产切 PostgreSQL**。用 SQLAlchemy 做 ORM 可以做到两者代码几乎一致，切换只改连接串。这样你在本地开发时不用装数据库，部署时也不吃亏。

**关键提醒**：复盘报告是这个产品的付费卖点，它需要做"按知识点聚合正确率""多次学习趋势对比"这类统计查询。**这类查询在关系型数据库里是一行 SQL 的事，在文档数据库里要写一堆应用层代码。** 这是我不推荐 MongoDB 的核心原因。

### 4.2 向量检索

先说一个判断：**MVP 阶段可能根本不需要向量库。**

你的 MVP 只做文字输入（通常几百到几千字），这段内容完全可以整体放进大模型的上下文里，不需要 RAG 检索。向量检索真正的用武之地是：输入是一本教材、一份长文档时，需要先切分再按需检索。

| 方案 | 优势 | 劣势 | 推荐场景 |
| --- | --- | --- | --- |
| **不引入（直接全文进上下文）** | 最简单、无额外依赖 | 受上下文长度限制 | ✅ MVP 阶段首选 |
| Chroma | 嵌入式、Python 原生、零配置、零成本 | 不适合大规模生产 | ✅ 开发期 |
| pgvector | 复用 PostgreSQL，一个库搞定 | 需要装扩展 | ✅ 生产环境推荐 |
| Milvus / Qdrant | 专业向量库、性能强 | 额外运维一个服务，对一人过重 | 规模大了再说 |
| 腾讯云向量数据库 | 托管免运维 | 成本、平台绑定 | 不想运维时的备选 |

**推荐策略**：MVP 不引入向量库；V1.0 做文档解析时，开发期用 Chroma、生产用 pgvector，这样生产环境始终只有一个数据库要维护。

## 5. 大模型接入选型

### 5.1 供应商对比

价格水平以 2026 年公开定价为参考，仅用于横向比较：

| 供应商 | 代表模型 | 价格水平 | 是否已备案 | 是否易拿到《合作协议》 | 备注 |
| --- | --- | --- | --- | --- | --- |
| **DeepSeek** | deepseek-flash / v4-pro | 极低 | 是 | 需核实 | 性价比最高；flash 缓存未命中输入 1 元/百万 token、输出 4 元/百万 token（空闲时段） |
| 阿里云百炼 | 通义千问系列 | 低 | 是 | ✅ 是（有成熟的客服对接流程） | **产品化申请深度合成类目时最省事** |
| 火山引擎 | 豆包系列 | 低 | 是 | ✅ 是 | 同阿里云 |
| 智谱 AI | GLM 系列 | 低 | 是 | ✅ 是 | 国内老牌 |
| 月之暗面 | Kimi | 中 | 是 | 需核实 | 长文本能力强，适合长文档场景 |
| 硅基流动 | 多模型聚合 | 低 | 取决于上游 | 否（聚合平台） | 适合做多模型对比测试 |
| OpenAI / Anthropic | GPT / Claude | 高 | 境内服务未备案 | — | **境内合规风险，不要作为唯一供应商** |

### 5.2 一个容易被忽略的关键判断

**模型供应商的选择不只是价格问题，它还影响你将来能不能拿到"深度合成"类目。**

微信在审核 AI 类小程序时，要求提交技术方的《互联网信息服务算法备案》以及**运营主体与技术主体的合作协议**。根据公开的实操记录，向阿里云申请这类合作协议是有成熟流程的（联系客服说明用途即可），而一些纯 API 供应商并不提供这项服务。

**所以结论是**：

- **开发阶段**：用 DeepSeek，成本最低，先把产品跑通
- **产品化阶段**：如果申请深度合成类目遇到合作协议的障碍，把主力模型切到阿里云百炼或火山引擎
- **架构要求**：**必须做模型适配层**，不能让业务代码直接依赖某一家 SDK。这是这份文档里最有实际价值的一条架构建议

### 5.3 适配层设计

不要在业务代码里直接写 `deepseek_client.chat(...)`。建议抽一层统一接口：

```
LLMProvider (抽象接口)
  ├── chat(messages, *, json_schema=None, temperature=...) -> str
  ├── chat_json(messages, schema) -> dict     # 结构化输出 + 校验 + 自动重试
  └── name / cost_estimate(tokens) -> float

实现：
  ├── DeepSeekProvider
  ├── BailianProvider      (阿里云百炼)
  ├── VolcengineProvider   (火山引擎)
  └── MockProvider         (离线开发与测试，不消耗额度)
```

`MockProvider` 尤其重要——它让你在没有 API key、没有网络、或者不想花钱的时候也能开发和测试（质量检测脚本里的 `--mock` 模式就是这个思路）。

## 6. 部署与运维选型

| 方案 | 优势 | 劣势 | 月成本估计 |
| --- | --- | --- | --- |
| **轻量云服务器 + Docker Compose** | 完全可控；可装任意组件；成本固定；本地与线上一致 | 需自己配域名、HTTPS、备案；有运维负担 | 首年约 38–99 元 |
| 微信云托管 | 免运维；与小程序内网直连（**可免备案域名**）；自动伸缩 | 与平台绑定；调试体验一般；成本随量增长 | 按量，早期约 30–200 元 |
| 腾讯云 CloudBase 云开发 | 数据库 + 存储 + 云函数一体；上手最快 | 以 Node.js 为主；复杂逻辑受限；迁移成本高 | 按量 |
| Vercel / 其他 Serverless | 部署极快、免费额度大 | 国内访问不稳定；小程序对 request 域名有备案要求 | 0–140 元 |

**推荐：轻量云服务器 + Docker Compose**。

理由很实际：

1. **域名和 HTTPS 是绕不过去的**。小程序要求所有网络请求走 HTTPS 且域名已备案，这件事无论用哪种方案都要处理（云托管的内网调用例外）。用服务器走一遍完整流程，你会真正搞清楚小程序后端的约束条件——这对作品集也是加分项。
2. **一个 Docker Compose 文件就能跑起 FastAPI + PostgreSQL + Redis**，可复现、可迁移，不会被任何厂商锁定。
3. **便宜**。早期 2 核 2G 的轻量服务器足够支撑几千用户。

> **买服务器时务必确认续费价。** 38–99 元是**新用户首年优惠价**，
> 续费价通常明显更高（有时是首年价的数倍）。购买前先看清续费价格，
> 别被首年低价误导。

**什么情况下应该重新考虑微信云托管**：你完全不想碰 Linux、不想备案、只想尽快上线。
但要注意两点：一是微信对"深度合成"类目要求**云环境有效期不低于 3 个月**；
二是云托管在内网调用上确实免备案，这是它相对轻量服务器唯一的硬性优势。
本次已确认选择轻量云服务器，四种方案的完整对比见第 11.2.4 节。

**开发阶段**：本地跑就行，用 `ngrok` 之类的内网穿透工具配合开发者工具的"不校验合法域名"选项做联调。不必一开始就买服务器。

## 7. 辅助技术选型

| 用途 | 推荐 | 备选 | 说明 |
| --- | --- | --- | --- |
| UI 组件库 | NutUI（Taro 官方适配） | Taro UI（较老）/ 自研 | 答题页核心交互建议自研，组件库只用来做基础控件 |
| 图表（复盘报告） | ECharts for 微信小程序（ec-canvas） | F2 / 自绘 canvas | 雷达图、趋势图 ECharts 现成；注意小程序端需要适配层 |
| 状态管理 | React Context + hooks | Zustand | MVP 阶段页面状态简单，Context 足够；不要过早引入重方案 |
| Markdown 渲染 | 服务端 markdown-it 转 HTML | towxml（小程序端渲染） | **推荐服务端渲染**，小程序端解析 Markdown 容易踩性能坑 |
| 动画 | CSS 动画 + 小程序原生动画 API | Lottie | 答题反馈用 CSS 就够，不要为 MVP 引入 Lottie |
| 音效 | 小程序 InnerAudioContext | — | 注意首次播放需用户交互触发，且要处理静音键状态 |
| 代码规范 | ESLint + Prettier + TypeScript strict | — | `strict: true` 一定要开，这是防大模型返回脏数据的第一道防线 |
| 包管理 | pnpm | npm / yarn | 快、省磁盘 |
| 后端测试 | pytest | — | 重点测"大模型返回异常结构"的容错分支 |
| 接口文档 | FastAPI 自动生成 OpenAPI | Apifox | 不用手写 |
| 日志与监控 | Python logging + 结构化日志 | Sentry | **至少要把每次 LLM 调用的 token 数和耗时记下来**，这是成本监控的基础 |

## 10. 明确不建议的方案

| 方案 | 不建议的理由 |
| --- | --- |
| Wepy、Remax、Chameleon | 社区已停滞，两年后遇到问题没人能帮你 |
| 小程序端直接调用大模型 API | API Key 会暴露在客户端；且小程序要求所有请求域名备案，无法直连 |
| 用 MongoDB 做主库 | 复盘报告的聚合统计会非常痛苦 |
| MVP 阶段就上 Milvus 等重型向量库 | 额外运维一个服务，而 MVP 可能根本不需要向量检索 |
| 同时引入多个 AI 框架（LangChain + LlamaIndex + 自研） | 一人开发时，框架的道德负担大于收益，容易陷入"调框架"而不是"做产品" |
| Java / Spring Boot | 对这个体量过重，开发速度最慢 |
| 只依赖单一未备案的境外模型 | 境内合规风险，且供应商出问题时会直接停摆 |

### 11.1 最终技术栈

| 层 | 选型 |
| --- | --- |
| 小程序前端 | Taro 4 + React 18 + TypeScript |
| UI 组件库 | NutUI（Taro 适配版，按需引入） |

### 11.2 关于选择轻量云服务器的说明

**最终结论（2026-09-14 二次确认）**：部署方案确定为**轻量云服务器 + Docker Compose**，
撤销此前"微信云托管"的选择。这一节说明为什么这样选、它有什么优势、以及你需要自己承担什么。

#### 11.2.1 推荐轻量云服务器的六个理由

| # | 优势 | 具体说明 |
| --- | --- | --- |
| 1 | **组件完全自由** | PostgreSQL + pgvector、Redis、向量库、文档解析依赖，想装什么装什么。这个项目后期要做文档/网页解析和向量检索，云托管在网络与存储上的限制可能变成"做不了"的硬约束 |
| 2 | **成本固定、可预测** | 新用户首年大致 **38–99 元**（阿里云轻量 2 核 2G 有 38 元/年秒杀价、常规优惠约 68 元/年；腾讯云 2 核 2G4M 约 99 元/年起）。云托管按量计费（CPU 0.055 元/(核·小时)、内存 0.032 元/(GB·小时)），流量波动时账单很难预估 |
| 3 | **本地与线上环境一致** | 一份 Docker Compose 编排文件，本地怎么跑线上就怎么跑，不会再出现"本地好使、线上不行" |
| 4 | **不被任何平台绑定** | 服务器可随时迁移，也能同时跑其他项目，不被单一生态锁死 |
| 5 | **调试最直接** | SSH 上去就能看日志、连数据库、改配置、抓包，不受云控制台功能的限制 |
| 6 | **作品集含金量更高** | 自己走完"域名 → 备案 → HTTPS → Nginx → 容器编排 → 部署"的完整链路，是能写进简历的工程能力；云托管把这一层全部遮住了 |

#### 11.2.2 代价：这些事需要你自己做

| 事项 | 说明 | 时间成本 |
| --- | --- | --- |
| 购买服务器 | 必须选**中国大陆节点**（境外节点无法备案） | 10 分钟 |
| 购买域名 | 域名的实名认证人必须是**你本人** | 10 分钟 |
| **ICP 备案** | 个人可以备案、**全程免费**，但需 **7–20 个工作日** | **最大的一项，必须提前启动** |
| SSL 证书 | Let's Encrypt 免费证书，或用云厂商提供的免费证书 | 30 分钟 |
| Nginx + HTTPS | 反向代理配置、证书自动续期 | 半天 |
| Docker 环境 | 安装 Docker、编写 compose 文件 | 半天 |
| 日常运维 | 系统更新、日志、备份、监控 | 持续投入 |

#### 11.2.3 一个必须提前知道的硬约束：备案主体必须一致

微信对小程序服务器域名有明确要求。多方文档（百度开发者中心、腾讯云、服务商指南）的一致表述是：

> 域名必须完成 ICP 备案，且**备案主体必须与小程序主体一致**。

落到你身上的具体含义：

- 你的小程序是**个人主体**，那么域名的备案主体也必须是**你本人**
- 域名实名认证的姓名与证件号必须与备案信息完全一致，**不能借用他人的域名**
- 服务器必须是**中国大陆节点**，香港及海外节点无法备案

个人备案本身完全可行，但有两点要注意：

1. **个人备案仅适用于非经营性网站。** MVP 与体验版阶段（不收费）没有问题；
   等到产品化、开始收会员费时，需要评估是否转为个体户 / 企业主体备案。
2. **部分省份（北京、上海、广东等）要求本地身份证或居住证、社保记录**，异地备案难度较大。

**因此建议：备案要尽早启动。** 备案免费，但 7–20 个工作日是整条部署路径上
唯一无法压缩的环节。可以先买服务器和域名、提交备案，审核期间照常做本地开发。

#### 11.2.4 四种部署方案横向对比

| 维度 | **轻量云服务器（推荐）** | 微信云托管 | 云开发 CloudBase | Serverless / Vercel |
| --- | --- | --- | --- | --- |
| 组件自由度 | **完全自由** | 受限 | 受限 | 受限 |
| 计费方式 | 固定包年 / 包月 | 按量（CPU 0.055 元/核·小时 等） | 按量 + 套餐 | 按量，有免费额度 |
| 成本可预测性 | **高** | 中 | 中 | 中 |
| 首年成本量级 | **38–99 元** | 免费额度约值 400 元（3 个月有效） | 视用量 | 0–100 元 |
| 域名备案 | **需要（7–20 工作日）** | 小程序内网调用可免备案 | 免备案（内网调用） | 需要，且国内节点受限 |
| 运维负担 | 高（自己管） | 低 | 最低 | 最低 |
| 调试体验 | **最直接（SSH）** | 中（看控制台日志） | 中 | 差 |
| 平台绑定 | **无** | 强 | 强 | 强 |
| 本地 / 线上一致性 | **高（Docker）** | 中 | 低 | 低 |
| 可迁移性 | **高** | 低 | 低 | 低 |
| 作品集含金量 | **高** | 中 | 低 | 低 |
| 适合场景 | **MVP → 产品化全程** | 快速原型、不想碰运维 | 极速 Demo | 静态站 / 边缘函数 |

**一句话总结**：轻量云服务器唯一的劣势是"要自己运维 + 要备案"，
而这两项对你恰好是**可以转化为优势的成本**——备案只需要等，
运维是作品集里最有说服力的内容。它换来的组件自由度，
在后期做文档解析和向量检索时会体现为"能做"和"做不了"的差别。

### 11.3 落地节奏

**当前范围（2026-09-14 确认）**：部署仍**暂缓实施**，先聚焦核心 MVP 的本地实现。
下面的节奏表用于规划时间，不需要现在执行。

## 附录 B：React 与 Vue 的差异（选型补充说明）

你已经熟悉 React，所以这一节的目的不是让你换技术，而是让你能清楚说出"我为什么选 React"——
这在面试和对外讲解时都会用到。

### B.1 两者的核心差异，其实只有一条

**React 把「界面」当成函数的结果；Vue 把「界面」当成数据绑定的模板。**

| 维度 | React | Vue |
| --- | --- | --- |
| 写法 | JSX：把 HTML 写进 JS 里，逻辑和结构混在一起 | 单文件组件（SFC）：`<template>` / `<script>` / `<style>` 三段分离 |
| 更新机制 | 数据不可变，调用 `setState` 显式触发重新渲染 | 响应式系统自动追踪依赖，数据一变视图自动更新 |
| 心智模型 | UI = f(state)，像写纯函数 | 声明式模板 + 指令（`v-if` / `v-for`） |
| 组件复用 | 自定义 Hook（`useXxx`） | 组合式函数（Composition API） |
| 生态形态 | 生态最大，但需要自己选型拼接（路由、状态、请求库各选一个） | 官方全家桶（Vue Router + Pinia + Vite），开箱即用 |
| 上手曲线 | 中等。语法本身简单，难点在 Hooks 的依赖数组和闭包陷阱 | 较低。有 HTML/CSS 基础的人几乎能立刻上手 |
| 性能优化 | 需要手动控制重渲染（`useMemo` / `useCallback` / `memo`） | 响应式粒度更细，多数场景无需手动优化 |
| 中文资料 | 多，但官方文档以英文为主 | 官方中文文档质量极高，社区中文内容密集 |
| 跨端方案 | Taro、React Native、Expo | uni-app（多端覆盖最全，含 App 和鸿蒙） |
| 就业市场 | 岗位数量更多，尤其大厂和海外公司 | 国内中小企业和外包项目占比高 |

### B.2 各自的优势

**React 的优势**

1. **生态最大**。几乎任何需求都有成熟库，这个项目的答题动画、图表、Markdown 渲染都能直接找到现成方案。
2. **跨端路径多**。Taro（小程序 + H5）、React Native（App）都用同一套心智，将来想扩展端，学习成本最低。
3. **对 AI 辅助编码最友好**。训练语料里 React 代码量最大，你让 AI 帮你写 Taro 页面时，它给出的代码质量明显更稳。
4. **概念少而统一**。整个框架的核心就是"组件 + props + state + Hooks"，没有额外的指令系统要记。
5. **就业与作品集观感更好**。简历上写 React + Taro 比写 Vue 更容易被前端岗位认可。

**Vue 的优势**

1. **上手最快**。模板语法接近 HTML，`v-for` 就是"循环一下"，对新手最友好。
2. **官方方案统一**。不用纠结"路由用哪个、状态管理用哪个"，官方都给了标准答案，这对一个人做项目是真实的减负。
3. **中文文档和中文社区质量最高**。遇到问题更容易搜到中文答案。
4. **uni-app 的多端能力最强**。如果你的目标是"一套代码同时出微信小程序、支付宝小程序、抖音小程序和 App"，Vue + uni-app 是唯一顺滑的选择。
5. **响应式自动更新**。不用手动管理依赖数组，也就不会踩 React 里最常见的那些坑。

### B.3 对你的结论

**继续用 React + Taro，不要因为"Vue 更简单"而切换。**

理由很直接：Vue 相对 React 的主要优势是**学习成本低**，而对你来说这部分成本已经是零——你本来就会 React。
用一个你不熟的技术去换取"节省学习成本"，是净亏损。

唯一值得重新考虑的情况是：**如果你的目标变成"必须同时覆盖支付宝、抖音等多个小程序平台"**，
那时 uni-app 的多端优势才真正压过 React 的生态优势。但你当前的需求是微信小程序优先，
而且 Taro 本身也能编译到其他端，所以这个条件目前不成立。
